# Восстановление соединений и история - 1.7.0

## Явное восстановление потоков

```python
old = await client.market.subscribe_tickers()
# После ConnectionError либо по явному решению приложения:
replacements = await client.market.reconnect([old])
new = replacements[old.path]
```

Сохраните исходные ссылки: после разрыва внутренний каталог может быть очищен. Восстанавливаются только перечисленные подписки. Старые активные очереди завершаются с MarketStreamGap; ожидающие потребители получают явное сообщение о возможном пропуске. Новые подписки возвращаются после подтверждения сервером всего набора. При ошибке или отмене частичный набор закрывается. Старая ссылка close не отписывает новую подписку.

Приватные потоки поддерживают такой же reconnect([old_account_subscription]); возвращается словарь новых AccountSubscription по path. Также доступен old_account_subscription.resubscribe(). Подписки предыдущего входа нельзя переносить через logout/login. После refresh используется актуальная генерация токена. После переподключения сверяйте баланс и ордера через REST.

Автоматический replay событий не подтверждён. Снимок REST и push не имеют проверенного общего sequence-id, поэтому SDK не обещает атомарного восстановления L2 или полного списка событий за разрыв. После reconnect приложение должно сверить состояние и учитывать эту границу.

## История транзакций

```python
from bitteam_sdk import transaction_evidence

async for row in client.iter_transactions(page_size=100, max_pages=100):
    evidence = transaction_evidence(row, source="spot_transaction")
    # tx_hash исключён из repr; доступен явно при необходимости.
```

get_transaction_history читает /transactionsByUser, iter_transactions ограничивает страницы и удаляет повторяющиеся ID. Повтор целой страницы и исчерпание лимита дают ошибку, а не молчаливое усечение. Для истории транзакций требуется собственное поле id; trade_id и orderId не используются вместо него. Приватный обход привязан к исходной сессии аккаунта и прерывается при logout/login, в том числе между выдачей строк одной страницы. Refresh той же сессии допустим. Offset-пагинация не является серверным снимком: новые записи во время обхода могут сдвигать страницы. from/to передаются как start/end целыми числами без догадки о дополнительных фильтрах.

transaction_evidence обрабатывает известные поля записи. Для spot -1=failed,0=pending; для P2P type=withdraw -1=cancelled,0=created,1=pending. Неизвестные числа и строки остаются unknown. UI default-success не копируется. Источник и raw_status сохраняются; успешное завершение и окончательность блокчейна не выводятся из недоказанного значения. Для spot используется params.tx_id, при params.internalTransfer хеш не отображается. Поля не доказывают связь orderId с transaction.id.

## Границы проверки

Публичный reconnect проверен на живом сервере: новая подписка получила tickers, старая сообщила gap. Проверка аккаунта остановилась при restore: HTTP409/code409003. По словарю сайта это ошибка получения P2P-кода; конкретный endpoint и причина серверного отказа этим не установлены. Эта запись историческая; профиль сессии main позднее удалён по запросу пользователя и не восстанавливался. Приватный reconnect проверен синтетическими сценариями, но в этом выпуске не подтверждён живым аккаунтным прогоном.

## Владение приватными ресурсами

Ранее выданные P2P/account-stream/archive ссылки проверяют не только свой auth и lifecycle, но и принадлежность реального REST-владельца тому же объекту auth. Замена client.rest.auth делает старые приватные ссылки недействительными, даже если lifecycle A не менялся; refresh того же auth допустим. Ожидающий приватный consumer проверяет владельца после возобновления и не возвращает данные прежнего аккаунта. Anonymous market/history/site и публичные чтения archive/P2P не блокируются из-за этой замены. Прямое присваивание rest.auth не обещает немедленного пробуждения всех ожидающих задач.

Detach auth также увеличивает lifecycle прежнего SessionAuth: A -> B -> A не оживляет старую операцию, даже если fake I/O подавляет отмену. Старые подписки отклоняются; новые запросы/refresh/подписки вернувшегося A используют новую эпоху. Это не очищает cache/token/generation и не переносит старый jar.

## Отмена и неопределённое подтверждение подписки

SUB/UNSUB одного пути сериализованы до ACK. Если подтверждение потеряно из-за
отмены, timeout или ошибки, серверное состояние неизвестно: соединение выводится
из использования, остальные подписки получают сигнал разрыва. Следующий connect
ждёт защищённого cleanup; неуспешный close остаётся ошибкой. Отмена ожидающего
caller не делает retiring socket снова пригодным. Повторный subscribe требует
нового соединения и сверки состояния; автоматический replay не обещается.
Старая ссылка close повторно проверяет владельца пути после ожидания lock.

Archive.close использует общий cleanup task: отменившийся caller не отменяет
закрытие, параллельные/последующие callers видят его результат или ту же ошибку.
REST-операции привязаны к эпохе transport.auth, в том числе для API-ключей:
возврат A после A -> B -> A не оживляет ранее начатый приватный запрос.

## Explicit recovery history-подписок

`await client.history.reconnect(old_subscriptions)` возвращает словарь новых
подписок по исходному `path`, после ACK всего запрошенного набора. Передайте
сохранённые history-ссылки этого клиента с неизменёнными symbol/interval/path.
Дубликаты пути объединяются. Все прежние активные ссылки, включая не включённые
в новый набор, получают `KlineStreamGap` (`ConnectionError`, экспорт SDK).
Буфер старой ссылки очищается до закрытия соединения; ожидание consumer
пробуждается gap-сигналом. Старый close не отписывает замену.

Ошибка/отмена reconnect закрывает частичный набор, не возвращая частичный map.
После такого сбоя можно явно повторить reconnect с исходными ссылками. Сверьте
пропущенное окно через history REST/get_klines с checkpoint/bounds приложения;
reconnect сам не загружает и не воспроизводит свечи, не обещает sequence-id,
непрерывности или atomic snapshot+push. Это локальная orchestration-гарантия,
проверенная fake nes peers, а не новый подтверждённый серверный replay-контракт.

Account-итераторы после terminal/gap не вызывают скрытый connect при чтении.
Восстановление аккаунтных ссылок явно запрашивается через reconnect/resubscribe
в том же auth lifecycle. При смене generation между приватными SUB отправляется
REAUTH актуального токена; после смены аккаунта старые ссылки остаются запрещены.
Синтетические проверки подтверждают cleanup при отмене второго SUB и явный
повтор набора, но не доставку/порядок публикаций на реальном сервере.

## Отмена авторизации

Tracked auth I/O остаётся учтённым до завершения даже если transport подавляет
отмену. Наблюдаемая отмена caller сохраняется; поздний response не устанавливает
новые токены. Cleanup ждёт дочернюю операцию и может зависеть от transport deadline;
не обещается немедленный выход при некорректном transport, игнорирующем отмену.
Удалённый исход уже отправленного refresh неизвестен; отмена не означает его
откат или валидность прежних credentials. Автоматического replay нет.
Общий API-v2/P2P refresh endpoint по-прежнему не установлен.

## Bounded history backfill и snapshot reconciliation

`await client.recover_klines(old_subscription, start=start, end=end, **bounds)`
(также standalone `recover_klines`) сначала явно заменяет history-подписку,
затем читает существующим bounded API окно `[start,end)` в UTC seconds.
`KlineRecovery.candles` содержит tuple полученных свечей, `subscription` — новый
итератор; `start/end` нормализованы. Полная валидация bounds происходит до
reconnect. История и live-буфер возвращаются отдельно: timestamp может пересекаться,
открытая свеча может измениться, а ограниченная очередь может переполниться.
SDK не выбирает за приложение приоритет пересекающихся данных, не добавляет
пустые свечи и не выставляет флаг полноты. Пустой интервал не доказывает packet
loss или полноту архива. При ошибке/отмене backfill созданная подписка закрывается;
повторная отмена не теряет cleanup. Транспорт принадлежит caller и остаётся его
ответственностью. Все старые refs shared history connection получают gap.

`await client.reconcile_book(symbol, old_subscription)` (также standalone
`reconcile_book(client, symbol, old_subscription)`) проверяет владельца, канал
orderbook и pairId по существующему public pair lookup, затем reconnect и свежий
REST snapshot. `ReconciledBook` возвращает snapshot и новый raw-event iterator;
`continuity_guaranteed=False`, `events_applied=False` неизменяемы. Буфер push
не сливается со snapshot. Старый gap сохраняется, все прочие refs той же market
connection также инвалидируются обычным reconnect. Ошибка snapshot закрывает
созданную подписку, сохраняя исходную ошибку/отмену. Это reconciliation двух
наблюдений, не восстановленная непрерывная L2-книга.

Доказанного snapshot anchor, monotonic sequence, delta semantics или replay
контракта нет. Неиспользуемые first/lastUpdateId в старом JS не устанавливают
этот контракт. Приложение должно самостоятельно выбрать политику дальнейших
snapshot-проверок и обработки raw events; SDK не выдаёт такую книгу за atomic.

TOTP/device/code-send сериализованы с login. После ожидания проверяются
owner/lifecycle/state, поэтому старый challenge не пересекает повторный вход и
поздний ответ не понижает READY. При ошибке или отмене lock освобождается для
явной новой попытки; автоматического re-login/OTP нет. Контекстные менеджеры
client/REST и owned history cleanup сохраняют первичную ошибку/отмену; ошибка
самостоятельного close по-прежнему видима и не означает successful cleanup.

## Владелец многошагового recovery

History/market/account streams, выданные BitTeamClient, проверяют его liveness
перед connect/allocation/dispatch и после await. После client.close() такой
held stream не может открыть новое соединение. Это отдельная публичная owner-
граница, не SessionAuth. Самостоятельный BitTeamWebSocket без владельца остаётся
повторно подключаемым после его close; явный reconnect при открытом владельце
также сохраняется. Cleanup никогда не блокируется owner-guard.

recover_klines/reconcile_book проверяют владельца между стадиями (и между
history chunks), сохраняют отмену caller, даже если compatible I/O подавляет
CancelledError, и дожидаются дочерней операции. Поздний успех не возвращается,
следующая стадия не запускается. При закрытом владельце выполняется cleanup
всего захваченного transport, включая поздно открытое соединение; не только
replacement ref. Drain может ждать transport deadline, немедленный выход для
неисправного I/O, игнорирующего отмену, не обещается. Это не replay/atomicity.

MarketDataRecorder использует только file-backed SQLite. ':memory:' (str/Path)
отклоняется до I/O: новый connection на операцию не сохранял историю. Для
in-memory свечей используйте SQLiteStorage с его отдельным lifetime-контрактом.
Recorder держит lock до завершения SQL worker даже при отмене read/insert;
частичный DDL connection закрывается, первичная SQL/decoder ошибка не маскируется
вторичной close-ошибкой. Самостоятельная ошибка close остаётся видимой.
